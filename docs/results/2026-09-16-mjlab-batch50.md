# 2026-09-16 mjlab batch50

Status: Complete
Last verified: 2026-09-16
Experiment: [LIBERO mjlab in the Sim2Real workspace](../../../../docs/experiments/libero-mjlab.md)

## Result

Batching 50 worlds improves mjlab controller-plus-physics throughput by 2.35×
per environment compared with one world. It is 1.27× faster than the matched
serial native baseline. GPU success is 139/150 replays (92.7%); native success
is 150/150. Perfect GPU replay is not an acceptance requirement for this
comparison, but the measured success difference remains part of the result.

Each episode contains 103 control actions. Times below are medians of three
complete runs after warmup. Amortized time divides batch time by world count;
all worlds in a GPU batch still take the full batch duration to finish.

### Original CPU controllers plus physics

| Backend | Worlds | Batch seconds | Seconds / environment, amortized | ms / action / environment, amortized | Success per repeat |
|---|---:|---:|---:|---:|---|
| Native MuJoCo | 1 | 1.801 | 1.801 | 17.486 | 1, 1, 1 / 1 |
| mjlab GPU | 1 | 3.667 | 3.667 | 35.604 | 1, 1, 1 / 1 |
| Native MuJoCo, serial | 50 | 98.675 | 1.974 | 19.160 | 50, 50, 50 / 50 |
| mjlab GPU | 50 | 77.868 | 1.557 | 15.120 | 47, 48, 44 / 50 |

Measured batch ranges: native 1, 1.793–1.847 s; GPU 1, 3.610–3.713 s;
native 50, 98.434–98.894 s; GPU 50, 77.547–78.400 s.

### Physics-only torque replay

| Backend | Worlds | Batch seconds | Seconds / environment, amortized | Success per repeat |
|---|---:|---:|---:|---|
| Native MuJoCo | 1 | 0.409 | 0.409 | 1, 1, 1 / 1 |
| mjlab GPU | 1 | 1.641 | 1.641 | 1, 1, 1 / 1 |
| Native MuJoCo, serial | 50 | 23.878 | 0.478 | 50, 50, 50 / 50 |
| mjlab GPU | 50 | 2.692 | 0.054 | 39, 43, 46 / 50 |

Measured batch ranges: native 1, 0.409–0.413 s; GPU 1, 1.628–1.657 s;
native 50, 23.642–23.886 s; GPU 50, 2.686–2.731 s.

Physics throughput reaches 47,830 environment physics steps/s at 50 worlds.
That is 30.48× the single-world GPU throughput and 8.87× the serial 50-world
native throughput. This scope omits feedback control and has lower success,
128/150, so its speedup must not be presented as full-environment performance.

The large difference between these scopes points to the retained CPU
controllers, CPU forward calculations, and synchronization as the remaining
bottleneck. The experiment does not separately profile their contributions.

All measured states were finite. The native benchmark loop matched ordinary
LIBERO stepping exactly (maximum flattened-state difference 0). No solver or
buffer-overflow warnings appeared. The 50-world success rate is evidence for
this replay only, not a suite-wide or statistically independent success estimate.

- Task: `libero_spatial/pick_up_the_black_bowl_from_table_center_and_place_it_on_the_plate`.
- Input: `demo_0` from the task's `_demo.hdf5`, 103 expert actions, 25 physics steps per action.
- Dataset SHA-256: `75ede0cf5fbfc925093671b55032ad80f1b1f1cf35442ec6c663460d37d3e0b3`.
- Hardware: one NVIDIA L40S on `simeval-rutavms-molmospaces-high-priority`.
- Stack: mjlab 1.6.0, MuJoCo and MuJoCo-Warp 3.11.0, robosuite 1.4.0,
  PyTorch 2.7.1, Warp 1.16, Python 3.11.
- CPU execution: one Torch thread; `OPENBLAS_NUM_THREADS`, `OMP_NUM_THREADS`,
  and `MKL_NUM_THREADS` all set to 1.
- One complete warmup and three measured episodes per configuration and scope.
  GPU synchronization brackets each timer. Reset and setup are outside timing.

Every world receives the same recorded initial state and expert actions. Each
has independent simulation data and its own original CPU OSC controller. The
GPU uses one shared-model, 50-world mjlab Simulation with bulk control uploads
and state downloads at every physics substep. Native MuJoCo runs worlds serially.

The benchmark refreshes controller pose and goals from the injected initial
state for both backends. Before timing, its native controller loop must succeed
and match ordinary LIBERO stepping within `1e-7` maximum flattened-state error.
Cameras, observation construction, policy inference, and final success checks
are excluded. These timings cannot be directly compared with the earlier
[camera-enabled replay](2026-09-16-mjlab-replay.md).

## Limitations

This measures one task, one initial state, and one action sequence. Repeats are
timing replicates, not independent samples of task generalization. The CPU
baseline is serial, not a multicore vector runner. GPU task outcomes may vary
because contact reductions are nondeterministic.

Physics-only replay uses precomputed native torques resident on GPU and omits
controllers and per-step host readback. Its throughput is not complete LIBERO
environment throughput. The runner is a benchmark bridge; the regular
`OffScreenRenderEnv` remains single-world and has no batched camera API.

- ~~`batch50-measured`~~: failed native loop parity before accepting timings.
- ~~`batch50-measured-v2`~~: native loop parity passed, but native task success failed;
  stopped before completing the matrix.
- ~~`batch50-resetcheck`~~: failed the native success gate after reset-only changes.

The accepted run refreshes the controller's cached pose and goals after state
injection. This initialization is explicit in the benchmark and does not change
the production backend. Failed runs are excluded from the timing comparison.
